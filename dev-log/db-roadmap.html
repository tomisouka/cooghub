Why a database

Current persistence is file-based JS: memory-deadlines.js, memory-progress.js, flat JSON. It works for simple state but breaks down the moment you want to query — "which skills did I level up this week", "which PDFs have I read", "what's my streak", "show me flashcard history". Files are not queryable. DB is.

The other driver is the content model. Right now subjects.js is a 600+ line hand-edited JS object. Every new file requires a manual patch. A DB with a seed from the existing manifest gives us queryable content, per-file metadata, read tracking, and bookmarks — without rebuilding anything.

This is not a rewrite. It's a persistence layer upgrade. All React state stays React state. The DB handles what files can't: history, queries, relationships, and sync logs.

Key Decisions
? Which SQLite library — rusqlite vs sqlx vs tauri-plugin-sql?
rusqlite is the right call. Synchronous, no async complexity, well-documented, and all DB work happens in Rust commands anyway — React never touches the DB directly. sqlx async overhead is unnecessary here. tauri-plugin-sql exposes the DB to JS which is exactly what we don't want.
→ rusqlite
? Where does the DB file live?
~/.coogshub/coogs.db — same pattern as ~/.coogshub_path. Lives outside the project so it's never accidentally committed, survives pnpm build, and is easy to find/backup. SyncThing can optionally sync it between machines if the path is added to the sync config.
→ ~/.coogshub/coogs.db
? Browser mode — how does the Express server access SQLite?
Use better-sqlite3 in Express. Same DB file path, same schema. Each Express route mirrors its Rust command. The two runtimes share the same DB file when running on the same machine — no sync needed locally.
→ better-sqlite3 in Express, same DB path
? Migration strategy — how to move from file-based to DB without data loss?
On first launch after DB is introduced: check if memory-deadlines.js / memory-progress.js exist on disk. If yes, read them and insert into DB, then rename to *.migrated. Subsequent launches skip migration. This is a one-time, zero-loss path. No manual steps required.
→ auto-migrate on first launch, rename originals
? Single DB file or separate files per domain?
Single file. Simpler backup, simpler sync, simpler Rust connection management. SQLite handles concurrent table access fine within one file. Splitting by domain adds complexity with no real benefit at this scale.
→ single coogs.db
Risks
Risk Impact Mitigation Level
Data loss during migration from memory-*.js Skill levels / deadlines wiped Auto-migrate reads files first, writes DB, only then renames originals. Files stay as .migrated backup. Low
rusqlite compilation on both machines Build fails on kusuo (laptop) rusqlite bundles SQLite — no system dependency. Should compile clean on both machines with same Rust toolchain. Low
Express + rusqlite DB file contention Corruption if both open at same time SQLite WAL mode handles concurrent readers. Express and Tauri won't run simultaneously on same machine in normal use. Medium
subjects.js and DB get out of sync Files appear in DB but not in UI (or vice versa) Seed script is idempotent. During transition period, both are in sync by design. Phase 6 removes subjects.js as source of truth. Medium
SyncThing syncing DB file between machines causes conflicts One machine's data overwrites the other Don't sync coogs.db via SyncThing. Each machine has its own DB. Git syncs code, SyncThing syncs content files — DB stays local per machine. Revisit in Phase 7 with sync_log. High if synced
