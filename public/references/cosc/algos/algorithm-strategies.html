Algorithmic Thinking:
Three Core Strategies

Brute Force, Decrease & Conquer, and Divide & Conquer — what they are, how they differ, and when each appears.

§ 0 — Introduction

Why strategy matters before code

Every algorithm belongs to a design paradigm — a mental framework for attacking a problem. Before you write a single line, choosing the right strategy determines your complexity ceiling.

∀
Brute Force
Try everything. No cleverness. Direct exhaustive attack on the problem.
n−1
Decrease & Conquer
Shrink the problem by one (or a constant) each step. Use the smaller answer to get the full answer.
n/2
Divide & Conquer
Split into independent halves. Solve both. Merge. Each split is where the log n comes from.
The key question to ask
Brute Force: "What's the most direct way to try all possibilities?"
Decrease & Conquer: "How do I reduce this to size n−1?"
Divide & Conquer: "How do I split this into independent halves?"
§ 0.1 — The Critical Distinction

Decrease vs. Divide — these get confused most

Both are recursive/iterative. Both exploit structure. The difference is in what you do after:

Decrease & Conquer

You solve a problem of size n−1, then extend that solution to size n. One subproblem. The reduction is sequential — each step depends on the previous.

Divide & Conquer

You split into two (or more) independent subproblems of size ~n/2, solve both, then combine. Neither half needs the other to run.

Exam tip: If the recursion only goes one direction (and one side is always trivially handled), it's probably Decrease & Conquer. If both halves do real work and you need a merge step, it's Divide & Conquer.
§ 1 — Brute Force

Brute Force

Solve the problem by directly trying all possibilities with no exploitation of structure. The algorithm does exactly what the problem statement says, naively. Often the first correct solution — never the best efficient one.

Core idea
There is no strategy. For every possible candidate, check if it's the answer.
Correctness is trivial. Efficiency is not.
Best caseO(1)
Average caseO(n)
Worst caseO(n²) or worse
§ 1.1 — Example: Linear Search

Linear Search

Check every element from left to right. Return when found. No assumptions about order.

linear_search.py Python 
def linear_search(arr: list, target: int) -> int:
    # Brute force: check every index, no assumptions made
    for i in range(len(arr)):
        if arr[i] == target:
            return i       # found at index i
    return -1          # not found

# Example
arr = [5, 3, 8, 1, 9, 2]
print(linear_search(arr, 8))   # → 2  (index of 8)
print(linear_search(arr, 7))   # → -1 (not present)

§ 1.2 — Example: Naive String Matching

Naive String Matching

Try aligning the pattern at every position in the text. At each alignment, check character by character. Classic O(nm) brute force.

naive_string_match.py Python 
def naive_search(text: str, pattern: str) -> list:
    n = len(text)
    m = len(pattern)
    matches = []

    # Try every alignment: O(n) positions
    for i in range(n - m + 1):
        # Check character by character: O(m) per alignment
        if text[i:i + m] == pattern:
            matches.append(i)

    return matches   # T(n) = O(n * m)

print(naive_search("AABAACAADAABAABA", "AABA"))
# → [0, 9, 12]
Why brute force is still useful: It's trivially correct. Use it to verify faster algorithms on small inputs. On exams, describing the brute force first shows you understand the problem before optimizing it.

§ 2 — Decrease & Conquer

Decrease & Conquer

Reduce the problem by one (or a constant factor, or a variable amount) each step. Solve the reduced problem, then extend that solution to the original. The key is that you're recursing into one subproblem — not two independent ones.

Core idea
T(n) = T(n−1) + O(1) → O(n)
T(n) = T(n/2) + O(1) → O(log n)
T(n) = T(n−1) + O(n) → O(n²)
Three flavors

Decrease by 1: Selection Sort, Insertion Sort — problem shrinks by one element each pass.

Decrease by constant factor: Binary Search — problem halves each step.

Decrease by variable: Quickselect — partition removes a variable chunk.

One subproblem only

This is what separates D&C from Divide & Conquer. After reducing, you recurse into one subproblem. The other part is either trivially done or discarded entirely.

§ 2.1 — Example: Selection Sort

Selection Sort

On each pass, find the minimum of the unsorted suffix and lock it in place. After k passes, the first k elements are sorted. The problem decreases by one each round.

Best caseΘ(n²)
Average caseΘ(n²)
Worst caseΘ(n²)
Note: Selection Sort has no best-case improvement — it always scans the full remaining unsorted portion regardless of input order. At most n swaps total (one per pass), which is its only real advantage over Bubble Sort.
selection_sort.py Python 
def selection_sort(arr: list) -> list:
    n = len(arr)

    for i in range(n):
        # Find minimum in unsorted suffix arr[i..n-1]
        min_idx = i
        for j in range(i + 1, n):
            if arr[j] < arr[min_idx]:
                min_idx = j

        # Swap min into position i — lock it in
        arr[i], arr[min_idx] = arr[min_idx], arr[i]
        # Problem reduced: arr[0..i] is now sorted

    return arr

print(selection_sort([5, 3, 8, 1, 9, 2]))
# → [1, 2, 3, 5, 8, 9]

§ 2.2 — Example: Binary Search

Binary Search — decrease by constant factor

Each step throws away half the search space. This is decrease-and-conquer by a factor of 2, giving O(log n). Requires a sorted array.

Best caseO(1)
Average caseO(log n)
Worst caseO(log n)
binary_search.py Python 
def binary_search(arr: list, target: int) -> int:
    low, high = 0, len(arr) - 1

    while low <= high:
        mid = (low + high) // 2

        if arr[mid] == target:
            return mid              # found
        elif arr[mid] < target:
            low = mid + 1            # discard left half
        else:
            high = mid - 1           # discard right half

    return -1   # not found
    # T(n) = T(n/2) + O(1) → O(log n) by Master Theorem Case 2

arr = [1, 2, 3, 5, 8, 9, 13, 21]
print(binary_search(arr, 9))   # → 5

§ 3 — Divide & Conquer

Divide & Conquer

Split the problem into independent subproblems, solve them recursively, then combine the results. The independence of subproblems + the merge step is where the log n comes from and what makes these algorithms hard to analyze.

Recurrence form
T(n) = aT(n/b) + f(n)

a = subproblems, b = size reduction factor, f(n) = work outside recursion
→ Solve with Master Theorem
Three phases (always)

Divide: Split input into b parts of size n/b.

Conquer: Recursively solve each part. Base case when n is small enough.

Combine: Merge subproblem solutions into the full answer. This step is often the expensive part.

What makes it different

Both halves do real work. Neither is discarded. And you need a non-trivial merge step to stitch results together. If one half is trivially empty, you're doing decrease-and-conquer.

§ 3.1 — Example: Merge Sort

Merge Sort

Divide the array in half, sort both halves recursively, then merge them. The merge step does O(n) work. Recurrence: T(n) = 2T(n/2) + O(n) → O(n log n) by Master Theorem Case 2.

Best caseO(n log n)
Average caseO(n log n)
Worst caseO(n log n)
merge_sort.py Python 
def merge_sort(arr: list) -> list:
    # Base case: size 0 or 1 is already sorted
    if len(arr) <= 1:
        return arr

    # DIVIDE: split into two independent halves
    mid = len(arr) // 2
    left  = merge_sort(arr[:mid])    # T(n/2)
    right = merge_sort(arr[mid:])   # T(n/2)

    # COMBINE: merge two sorted halves — O(n)
    return merge(left, right)

def merge(left: list, right: list) -> list:
    result = []
    i = j = 0

    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]);  i += 1
        else:
            result.append(right[j]); j += 1

    return result + left[i:] + right[j:]
    # T(n) = 2T(n/2) + O(n) → O(n log n)

print(merge_sort([5, 3, 8, 1, 9, 2]))
# → [1, 2, 3, 5, 8, 9]

§ 3.2 — Example: Quicksort

Quicksort

Pick a pivot, partition everything around it (smaller left, larger right), then recursively sort both sides. Unlike Merge Sort, the hard work is in the divide step (partition), and the combine step is trivial.

Best caseO(n log n)
Average caseO(n log n)
Worst caseO(n²)
Quicksort vs Quickselect: They share the partition step. Quicksort recurses on both halves (divide & conquer). Quickselect recurses on one half only (decrease & conquer). Same code skeleton, different recursion structure, different complexity.
quicksort.py Python 
def quicksort(arr: list, lo: int, hi: int) -> None:
    if lo >= hi:
        return   # base case

    # DIVIDE: partition around pivot — O(n)
    p = partition(arr, lo, hi)

    # CONQUER: recurse on BOTH sides (this is what makes it D&C)
    quicksort(arr, lo, p - 1)    # left of pivot
    quicksort(arr, p + 1, hi)   # right of pivot
    # COMBINE: nothing — pivot already in final position

def partition(arr: list, lo: int, hi: int) -> int:
    pivot = arr[hi]   # last element as pivot
    i = lo - 1

    for j in range(lo, hi):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]

    arr[i + 1], arr[hi] = arr[hi], arr[i + 1]
    return i + 1   # pivot's final index

arr = [5, 3, 8, 1, 9, 2]
quicksort(arr, 0, len(arr) - 1)
print(arr)   # → [1, 2, 3, 5, 8, 9]

§ 4.1 — Common Exam Traps

Where students get it wrong

Trap 1

Bubble Sort is decrease & conquer, not brute force. It reduces the unsorted portion by one each pass — that's the defining characteristic of D&C by one.

Trap 2

Binary Search can be classified as either D&C or decrease & conquer depending on the framing. Gopal's textbook treats it as decrease by factor — one subproblem, other half discarded.

Trap 3

Quicksort vs Quickselect. Same partition code. Quicksort recurses on both sides (D&C). Quickselect recurses on one side only (decrease & conquer). Different paradigm, different complexity.

Trap 4

O(n²) does not mean brute force. Selection Sort is O(n²) and decrease & conquer. Complexity and design paradigm are orthogonal concepts.

§ 4.2 — Quick Classification Test

Ask these questions in order

Decision tree
1. Does the algorithm recurse at all?
   → NO: likely Brute Force (or Dynamic Programming)

2. How many recursive calls does it make?
   → ONE: Decrease & Conquer
   → TWO or more: Divide & Conquer

3. Is the subproblem size n−k or n/b?
   → n−k (constant subtracted): Decrease by constant
   → n/b (divided): Decrease by factor (or D&C)
