Computer Systems · Memory Architecture

Memory: A Complete Map

Stack, heap, global, local, program counter, stack frames — how memory is actually laid out and used when your program runs.

§ 0 — The Big Picture

How a program's memory is laid out

Every running program gets a block of virtual memory from the OS. That block is divided into distinct regions, each with a different purpose, lifetime, and access pattern.

Process virtual address space — high address → low address
0xFFFF…
Stack
Local variables, function parameters, return addresses, saved registers. Grows downward. Managed automatically by the compiler.
↓ ↑
unmapped gap — stack and heap grow toward each other
Heap
Dynamically allocated memory. malloc / new lives here. Grows upward. Must be freed manually (C) or by garbage collector (Python/Java).
BSS
Uninitialized global and static variables. Zero-filled at program start. Not stored in the binary.
Data
Initialized global and static variables. Stored in the binary, loaded directly into memory at startup.
0x0000…
Text / Code
Machine instructions. Read-only. The Program Counter (PC) always points somewhere inside this region.
The core rule
Stack = automatic, fast, limited size, LIFO, local scope, dies with function
Heap = manual/GC, flexible size, arbitrary lifetime, accessible via pointer
Data/BSS = globals and statics, entire program lifetime
Text = your compiled code — the PC walks through this region instruction by instruction
Every variable you write lands in exactly one region. Where it lands depends on where you declared it and how you allocated it — not on its type alone.

int main() {
    outer(3, 4);                  // stack frame pushed for outer
    return 0;
}
§ 1 — The Stack

The Stack

The call stack is a LIFO structure that tracks every active function call. Each call pushes a stack frame. When the function returns, its frame is popped. Everything on the stack has a fixed, compile-time-known size.

StructureLIFO
DirectionGrows ↓
AllocationAutomatic
SpeedVery fast
Size limit~1–8 MB
OverflowSegfault
What lives on the stack
• Local variables (size known at compile time)
• Function parameters
• Return address — where to jump back after the function
• Saved register values (callee-saved registers)
• Base pointer / frame pointer (rbp) — the frame's anchor

§ 1.2 — Stack Overflow

  
What happens when the stack runs out

  

    

      
How it happens

      
Each function call consumes stack space. Infinite (or extremely deep) recursion keeps pushing frames without popping. When the stack hits the OS-imposed limit (~1–8 MB), you get a segmentation fault.

      
Even non-recursive code can overflow: a char buf[5000000] inside a function tries to grab 5 MB on the stack.

    

    

      
How to fix it

      
Move large buffers to the heap via malloc. Convert deep recursion to iteration using an explicit stack data structure. Python's default recursion limit is 1000 — increase with sys.setrecursionlimit().

    

  

  

    
stack_overflow.cC

    
// ❌ Infinite recursion — stack exhausted → segfault
void infinite() {
    int x = 0;      // 4 bytes pushed on every call
    infinite();     // never returns
}

// ❌ Huge local array — stack killer
void big_local() {
    char buf[5000000];   // 5 MB on stack → boom
}

// ✅ Fix: large data belongs on the heap
void big_heap() {
    char* buf = (char*) malloc(5000000);
    // use buf ...
    free(buf);
}

  







  
§ 2 — The Heap

  
The Heap

  
The heap is a large pool for dynamic allocation — data whose size isn't known at compile time, or whose lifetime needs to outlive the function that created it. Unlike the stack, nothing is managed automatically: you free what you allocate (C/C++), or a garbage collector does it for you (Python, Java, Go).


  

    
StructureUnordered

    
DirectionGrows ↑

    
AllocationManual/GC

    
SizeGBs possible

    
SpeedSlower

    
BugsLeaks / UAF

  


  

    
What lives on the heap

    • Objects created with malloc / new / calloc / realloc

    • Arrays whose size is determined at runtime

    • Data that must outlive the function that created it

    • Linked list nodes, tree nodes, graph adjacency structures

    • In Python: literally every object — ints, strings, lists, dicts, all of it
  


  

  
§ 2.1 — Heap Fragmentation

  
Why the heap gets messy over time

  
As you allocate and free blocks, gaps develop between live allocations. These gaps may be too small to satisfy future requests individually — this is fragmentation. The allocator has to do extra bookkeeping to find usable space.

§ 2.2 — The Three Heap Bugs

  

    
heap_bugs.cC

    
// ❌ 1. Memory leak — allocated, never freed
void leak() {
    int* p = (int*) malloc(sizeof(int) * 100);
    // ... use p ... but never free(p)
    // 400 bytes lost for the life of the process
}

// ❌ 2. Use-after-free — classic undefined behavior + security bug
void uaf() {
    int* p = (int*) malloc(sizeof(int));
    *p = 42;
    free(p);
    printf("%d\n", *p);  // ❌ p is dangling — may crash, may corrupt
}

// ❌ 3. Double free — corrupts the allocator's internal state
void dfree() {
    int* p = (int*) malloc(4);
    free(p);
    free(p);  // ❌ undefined behavior
}

// ✅ Correct pattern — allocate, use, free, null
void correct() {
    int* p = (int*) malloc(sizeof(int));
    *p = 42;
    printf("%d\n", *p);
    free(p);
    p = NULL;    // null the pointer — prevents accidental UAF
}

  


  

    Python / Java heap note: In Python, every object lives on the heap — integers, strings, lists, functions, all of it. CPython uses reference counting plus a cyclic GC to free. You never call free(), but leaks can still happen via lingering references (a global list that accumulates objects forever). Java uses generational GC. Go uses tri-color mark-and-sweep. The heap is still there — you just don't manage it by hand.

§ 3.1 — All Four Storage Classes in One File

  

    
scope_lifetime.cC

    
int   g_count = 0;     // GLOBAL   — DATA, scope: entire file
int   g_zero;           // GLOBAL   — BSS,  zero-initialized

void counter() {
    static int calls = 0;   // STATIC LOCAL — BSS, persists across calls
    int        x     = 0;   // LOCAL AUTO   — STACK, fresh every call

    calls++;    // persists: 1, 2, 3 …
    x++;        // always 1 — reset each call
    g_count++;  // global — visible everywhere

    printf("calls=%d  x=%d  g=%d\n", calls, x, g_count);
}

int* heap_example() {
    int* p = (int*) malloc(sizeof(int));
    *p = 777;
    return p;   // safe — heap outlives the function frame
}

int main() {
    counter();   // calls=1, x=1, g=1
    counter();   // calls=2, x=1, g=2  ← x resets, calls doesn't
    counter();   // calls=3, x=1, g=3

    int* val = heap_example();
    printf("%d\n", *val);  // 777 — heap outlived heap_example()
    free(val);
}

  


  

  
§ 3.2 — The Dangling Pointer Trap

  

    Never return a pointer to a local variable. When a function returns, its entire stack frame is popped. Any pointer into that frame is now pointing at memory the program no longer owns. In C this is silent undefined behavior — the next function call may quietly overwrite it.
  

  

    
dangling.cC

    
// ❌ Returns address of a stack variable — UB
int* bad() {
    int x = 42;    // x is on the stack frame of bad()
    return &x;     // frame popped on return — x is gone
}

// ✅ Allocate on the heap — outlives the function
int* good() {
    int* p = (int*) malloc(sizeof(int));
    *p = 42;
    return p;      // heap persists — caller must free
}

// Python: this is a non-issue — all objects on the heap,
// GC manages lifetime, references keep objects alive automatically
def safe_in_python():
    items = [1, 2, 3]   # list object on heap
    return items          # GC keeps it alive while ref exists

  







  
§ 4 — Stack Frames & Program Counter

  
Stack Frames & The Program Counter

  
Every function call creates a stack frame (activation record). The program counter (PC, or instruction pointer / RIP on x86-64) is a CPU register holding the address of the next instruction to execute. Together these two mechanisms are the heartbeat of program execution.


  

    

      
Program Counter (PC / RIP)

      
A single CPU register holding one address inside the text segment. The CPU fetches, executes, then automatically increments PC. On a function call: PC is pushed onto the stack as the return address, then set to the callee's first instruction. On return: PC is restored from the stack.

      
The PC is the only "cursor" in the CPU. Every branch, loop, call, and return is just the CPU changing where PC points.

    

    

      
Stack Frame (Activation Record)

      
A contiguous block of stack memory created per function call. Contains: the function's local variables, its parameters (if passed on stack), the saved return address (old PC), the saved base pointer (RBP), and any callee-saved registers. Freed automatically when the function executes ret.

    

  


  

    
Anatomy of a stack frame (x86-64 C calling convention)

    [higher addr]  caller's frame

    ───────────────────────────────────

      function arguments (if > 6, spill onto stack)

      return address    ← saved PC (where to jump after ret)

      saved RBP         ← caller's base pointer / frame anchor

      local variables   ← RBP - offset addresses these

      saved registers   ← callee-saved: rbx, r12–r15

    ───────────────────────────────────

    [lower addr]   ← RSP (stack pointer) always points here

§ 4.2 — Assembly: What CALL and RET actually do

  

    
call_mechanics.asm (x86-64)ASM

    
; Calling outer(3, 4) from main

    mov  edi, 3            ; arg a → register rdi (1st arg)
    mov  esi, 4            ; arg b → register rsi (2nd arg)

; CALL does two things atomically:
;   1. push (PC + instruction_size) onto stack  ← this IS the return address
;   2. jump: set PC ← address of outer
    call outer

; ── inside outer's prologue ────────────────────────
outer:
    push rbp               ; save caller's frame pointer (rbp)
    mov  rbp, rsp          ; rbp = current rsp → anchor this frame
    sub  rsp, 16           ; reserve 16 bytes for locals (aligned)

    mov  [rbp-4], edi     ; store param a  at rbp-4
    mov  [rbp-8], esi     ; store param b  at rbp-8
    add  edi, esi
    mov  [rbp-12], edi    ; sum = a + b    at rbp-12

; ── epilogue / RET ──────────────────────────────────
    leave                  ; = mov rsp,rbp + pop rbp (restores both)

; RET does two things:
;   1. pop return address from stack
;   2. jump: set PC ← that address (back into main)
    ret

  


  

    Buffer overflow and the PC: The saved return address sits on the stack inside the callee's frame. If a local buffer overflows (writing past its bounds), it can overwrite the return address — causing ret to jump to attacker-controlled code. This is why stack canaries, ASLR, and NX bits exist.

§ 5.2 — The Exam Traps

  

    

      
Trap 1 — scope ≠ lifetime

      
A static local variable has function scope (only visible inside that function) but global lifetime (memory persists the entire program). These are independent axes.

    

    

      
Trap 2 — pointer vs pointee

      
int* p = malloc(4) — the pointer p is on the stack. The integer it points to is on the heap. One allocation, two different regions.

    

  

  

    

      
Trap 3 — return address vs function address

      
The saved PC (return address) in a stack frame points back into the caller's code in TEXT. The function's own instructions are also in TEXT, but at a different address.

    

    

      
Trap 4 — BSS vs DATA

      
Uninitialized globals go to BSS — not stored in the binary, zero-filled by the OS at load. Initialized globals go to DATA — stored in the binary. Both have global lifetime.

    

  


  

    
One-line memory model

    TEXT = code (PC walks here) | DATA/BSS = globals (forever) |

    STACK = locals + call frames (function lifetime, LIFO, automatic) |

    HEAP = dynamic data (manual/GC lifetime, arbitrary size and order)
