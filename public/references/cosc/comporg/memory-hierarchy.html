Cache, RAM, VRAM & Virtual Memory

The full memory hierarchy — from nanosecond CPU caches to gigabytes of virtual address space and GPU VRAM — what each is, why it exists, and how they work together.

§ 0 — The Memory Hierarchy

Why there are so many kinds of memory

CPUs can execute billions of instructions per second. But getting data from RAM takes hundreds of cycles. The solution is a hierarchy — layers of progressively larger, slower, cheaper memory between the CPU and the disk. Each layer acts as a buffer for the one below it.

§ 1 — CPU Cache

CPU Cache (L1 / L2 / L3)

Cache is fast SRAM sitting between the CPU and main RAM. When the CPU needs data, it first checks L1 — if present, that's a cache hit (~1–4 cycles). If not, it checks L2, then L3, then fetches from RAM (~200 cycles). This is a cache miss.

L1 latency1–4 cyc
L2 latency~12 cyc
L3 latency~40 cyc
RAM latency~200 cyc
L1 size32–64 KB
L3 size8–64 MB
Temporal vs Spatial Locality
Temporal locality: if you used address X recently, you'll probably use X again soon.
Spatial locality: if you used address X, you'll probably use X+1, X+2, … soon.

Caches exploit both. A cache line is typically 64 bytes — when you load one word,
the entire 64-byte block around it is fetched. That's spatial locality in hardware.

§ 1.2 — Why cache-friendly code matters
cache_locality.cC
// ✅ Cache-FRIENDLY: row-major traversal
// arr[0][0], arr[0][1], arr[0][2] ... are contiguous in memory
// Each cache line load covers 16 ints (64 bytes / 4 bytes)
int arr[1024][1024];
for (int i = 0; i < 1024; i++)
    for (int j = 0; j < 1024; j++)
        arr[i][j] += 1;    // ← sequential, cache-hot

// ❌ Cache-HOSTILE: column-major traversal on row-major array
// arr[0][0], arr[1][0], arr[2][0] ... are 1024 ints apart
// Every access is a cache miss — jumps 4096 bytes each step
for (int j = 0; j < 1024; j++)
    for (int i = 0; i < 1024; i++)
        arr[i][j] += 1;    // ← random jumps, cold cache

// The hostile version can be 5-10x SLOWER on the same hardware.
// Same O(n²) complexity. Entirely different cache behavior.
§ 1.3 — L1 vs L2 vs L3: The Three Levels
L1 — per core, split

Split into L1i (instructions) and L1d (data). Smallest (~32–64 KB each) but fastest — 1 to 4 cycles. The CPU checks here first on every load and store. Critical path for performance.

L2 — per core, unified

Larger (256 KB to 1 MB), slower (~12 cycles). Holds data that was recently evicted from L1. Still per-core, so no sharing contention.

L3 — shared across all cores

Large (8–64 MB), slower (~40 cycles), shared by all cores on the die. Acts as a last-resort before going to RAM. Core-to-core communication often goes through L3.

Cache coherence

When multiple cores share memory, their caches can hold stale copies. The MESI protocol (Modified, Exclusive, Shared, Invalid) keeps caches consistent — a fundamental multi-core hardware challenge.

§ 2 — RAM

RAM (Random Access Memory)

RAM is the main working memory of the system. Every running program's code, data, heap, and stack live here (or appear to via virtual memory). It's volatile — power off and it's gone. Modern systems use DRAM, which stores bits as tiny capacitor charges that must be periodically refreshed.

TechnologyDRAM
Latency~60–100 ns
Bandwidth50–100 GB/s
Typical size8–128 GB
Volatile?Yes
Cost/GB~$3–6
DRAM vs SRAM
SRAM (cache): 6 transistors per bit. No refresh needed. Fast. Expensive. Small.
DRAM (RAM): 1 transistor + 1 capacitor per bit. Needs refresh. Slower. Cheap. Dense.

This is why L1 cache is 64 KB and RAM is 64 GB — fundamentally different cells.
§ 2.1 — How RAM is physically organized
Rows and columns

DRAM is organized as a 2D grid of rows and columns. Accessing a row "opens" it into a row buffer. Accessing the same row again (row hit) is fast. Accessing a different row requires a precharge cycle — this is the latency you feel.

DDR (Double Data Rate) transfers on both clock edges. DDR5 (2023+) runs at ~4800–8400 MT/s per channel.

Channels and ranks

Modern systems have 2–8 memory channels. Each channel is an independent 64-bit bus to the CPU. Dual-channel roughly doubles bandwidth. Ranks are the number of independent DRAM chip groups on a DIMM.

Bandwidth = channels × bus width × clock rate. A dual-channel DDR5-5600 system gets ~89 GB/s peak.

§ 2.2 — RAM in the context of your program
ram_context.pyPython
import sys, tracemalloc

# RAM holds everything a running process needs:
# - The Python interpreter's own code (text segment → cache → RAM)
# - Your module's bytecode
# - The heap: every list, dict, int, str you create
# - The call stack: local variables, return addresses

tracemalloc.start()

big_list = [list(range(1000)) for _ in range(1000)]
# big_list → heap → RAM → probably NOT in L1/L2 cache
# First access to each 64-byte chunk: cache miss → RAM fetch
# Subsequent accesses: cache hit

snapshot = tracemalloc.take_snapshot()
stats = snapshot.statistics('lineno')
print(stats[0])   # shows how much RAM this allocation used

# Accessing sequentially = cache-friendly
total = sum(x for row in big_list for x in row)

# Random access = cache-cold, every access may hit RAM
import random
val = big_list[random.randint(0,999)][random.randint(0,999)]
§ 2.3 — What happens when RAM fills up
Out of RAM → the OS swaps to disk. When physical RAM is exhausted, the OS evicts pages (4 KB chunks) to the swap partition or page file on disk. The next access to that page triggers a page fault — the OS suspends the process, reads the page back from disk, then resumes. This is 1000–100,000x slower than RAM. A heavily swapping system becomes nearly unusable.
§ 3 — VRAM

VRAM (Video RAM / GPU Memory)

VRAM is the dedicated memory on your GPU. It stores textures, framebuffers, shader programs, and (increasingly) ML model weights. Unlike system RAM, VRAM sits on the GPU card itself and is connected to thousands of shader cores simultaneously — it's designed for massive parallel bandwidth rather than low latency.

TechnologyGDDR6/HBM
Latency~500–800 ns
Bandwidth400–3000 GB/s
Typical size4–24 GB
Volatile?Yes
Cost/GB~$80–200
The core difference from RAM
RAM: designed for low latency, general purpose, accessed by a few CPU cores
VRAM: designed for high BANDWIDTH, accessed by thousands of shader cores at once

GDDR6X: ~1 TB/s bandwidth. DDR5 system RAM: ~90 GB/s. VRAM is ~10x wider.

§ 3.2 — What lives in VRAM
Graphics workloads

Textures — compressed image data for 3D surfaces. A single 4K texture is 32 MB uncompressed.

Framebuffer — the current rendered frame. At 4K/60fps with HDR: ~50 MB for color + depth.

Vertex / index buffers — 3D mesh geometry. A complex scene may have hundreds of MBs.

Shader programs — compiled GPU code that runs on every vertex and pixel.

ML / compute workloads

Model weights — a 7B parameter LLM at FP16 = ~14 GB VRAM. This is why consumer GPUs with 8 GB struggle with large models.

Activations — intermediate tensors during forward/backward pass. Can dwarf the model size during training.

KV cache — during LLM inference, previous token attention keys/values are cached in VRAM to avoid recomputation.

§ 3.3 — GDDR vs HBM
GDDR6 / GDDR6X (consumer)

Chips soldered around the GPU die. Wide interface (256–384 bit). GDDR6X uses PAM4 signaling for ~1 TB/s. Used in RTX 4090, RX 7900 XTX. Cheaper, good density, limited by PCB trace routing.

HBM2e / HBM3 (data center)

Stacked DRAM dies connected via silicon interposer directly to the GPU. Massively wider bus (1024–2048 bit). 3+ TB/s on H100. Used in A100, H100, MI300X. Much more expensive but dominant for ML training.

VRAM is the hard limit for ML: If your model + activations don't fit in VRAM, you can't run it on that GPU without tricks like quantization (FP8/INT4), gradient checkpointing, CPU offloading, or model parallelism across multiple GPUs. This is why 24 GB GPUs sell at a massive premium for ML workloads.

§ 4 — Virtual Memory

Virtual Memory

Virtual memory is an OS abstraction that gives every process the illusion of having its own large, contiguous address space. The CPU's MMU (Memory Management Unit) translates virtual addresses to physical RAM addresses on every memory access. This enables isolation, protection, and RAM overcommitment.

Address space48–64 bit
Page size4 KB default
Huge pages2 MB / 1 GB
Page fault~100 µs
TLB hit~0 extra cycles
TLB miss~10–100 cyc
What virtual memory gives you
Isolation: process A cannot read process B's memory — different page tables
Overcommit: allocate more virtual space than physical RAM exists
Swapping: evict cold pages to disk when RAM is full, bring back on access
Shared memory: multiple processes can map the same physical page (shared libs, IPC)
Guard pages: unmapped pages used to detect stack overflows (OS signals SIGSEGV)
§ 4.1 — Page Table Visualization

Virtual → Physical page mapping

Each entry in the page table maps one virtual page number (VPN) to a physical frame number (PFN), or marks it as swapped to disk, or as not-yet-allocated.

Page table — 16 virtual pages (4 KB each = 64 KB virtual space)
Mapped → physical frame in RAM
Swapped → on disk (page fault on access)
Unmapped → not allocated
§ 4.2 — Address Translation: VA → PA
address_translation.txtConcept
Virtual address (48-bit on x86-64):
  [PML4 idx 9b] [PDP idx 9b] [PD idx 9b] [PT idx 9b] [offset 12b]

Translation steps (hardware, every memory access):
  1. CPU generates virtual address (VA)
  2. Check TLB (Translation Lookaside Buffer) — a small cache of VA→PA mappings
     HIT:  use cached physical address directly → ~0 cycles overhead
     MISS: walk the 4-level page table in RAM → ~10-100 cycles
  3. Page table walk returns Physical Frame Number (PFN)
  4. Physical address = PFN × 4096 + (VA & 0xFFF)
  5. Check if page is present (P bit):
     PRESENT:  access RAM at physical address
     NOT PRES: PAGE FAULT → OS takes over
       - If swapped: read from disk, update page table, resume
       - If invalid: segmentation fault (SIGSEGV)

TLB on modern CPUs:
  L1 TLB:  32–64 entries, 0 latency penalty
  L2 TLB:  1024–1536 entries, ~7-cycle penalty
  Miss → page table walk in RAM → ~50-100 cycles
§ 4.3 — Swap / Page File
What is swap?

When RAM fills up, the OS picks "cold" pages (not recently accessed) and writes them to a swap partition (Linux) or page file (Windows). The physical frame is freed for another process. If the evicted data is needed again, a page fault suspends the process, the OS reads it back, and execution resumes.

Swap performance

SSD swap: ~100 µs per page fault. HDD swap: ~10 ms. Either way, that's 1,000–100,000x slower than RAM. A system that's heavily swapping ("thrashing") grinds to a halt. Modern systems with SSDs tolerate light swapping; HDD swap is essentially unusable under load.

§ 4.4 — mmap and virtual memory tricks
virtual_memory.cC / Linux
#include <sys/mman.h>

// mmap: map a file directly into the virtual address space
// Pages are loaded on-demand (demand paging) — no upfront RAM cost
void* mapped = mmap(
    NULL,           // let OS choose virtual address
    file_size,      // how many bytes to map
    PROT_READ,      // permissions
    MAP_PRIVATE,    // copy-on-write; changes not written back
    fd,             // file descriptor
    0               // offset in file
);
// First access to each page → page fault → OS loads that 4 KB chunk
// This is how the OS itself loads your executable — demand paging

// Anonymous mmap: large allocation without malloc overhead
void* big = mmap(NULL, 1<30, PROT_READ|PROT_WRITE,
                  MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
// 1 GB reserved in virtual space — but NO physical RAM used yet
// Only allocated when actually touched (zero-page optimization)

munmap(mapped, file_size);   // release virtual mapping
Virtual memory ≠ swap: Virtual memory is the address translation mechanism (always on). Swap is one consequence — pages that don't fit in RAM get evicted to disk. You can have virtual memory without swap (embedded systems). Swap is just one policy that exploits virtual memory's "not present" page fault mechanism.

§ 5.1 — What actually happens when you access a variable
full_path.txtWalkthrough
int x = arr[i];   ← you write this. here is what happens:

1. CPU issues a LOAD for virtual address VA = &arr[i]

2. MMU checks TLB for VA:
   HIT  → physical address PA in ~1 cycle
   MISS → walk 4-level page table (~50-100 cycles)
          → check P bit:
             present  → PA found, update TLB
             swapped  → PAGE FAULT, OS reads from disk (~100µs)
             invalid  → SIGSEGV

3. Now we have PA. Check L1 cache:
   HIT  → data returned in 1-4 cycles ✓
   MISS → check L2 (~12 cycles)
     HIT  → data returned, loaded into L1
     MISS → check L3 (~40 cycles)
       HIT  → data returned, loaded into L1+L2
       MISS → fetch from RAM (~200 cycles)
              64-byte cache line loaded into L1+L2+L3
              data returned

Total worst case: TLB miss + page fault + L3 miss + RAM fetch
  ≈ 100µs (swap) + 200 cycles (RAM) ≈ millions of cycles at 3 GHz

Total best case: TLB hit + L1 hit
  ≈ 1-4 cycles — essentially free
§ 5.2 — Exam Traps
Trap 1 — Virtual memory ≠ RAM

Virtual memory is an address translation system. It can be backed by RAM, by disk (swap), or by nothing yet (lazy allocation). "64 GB virtual address space" doesn't mean 64 GB of RAM exists.

Trap 2 — VRAM ≠ faster RAM

VRAM has higher bandwidth but higher latency than DDR5. The GPU tolerates latency by running thousands of threads — while one thread waits for VRAM, others run. This is the opposite of how CPUs handle memory latency (caches).

Trap 3 — Cache is hardware, not software

You cannot directly control what's in cache (without special intrinsics). You influence it indirectly by how you access memory. Sequential access = cache-friendly. Pointer chasing = cache-hostile.

Trap 4 — malloc doesn't touch RAM immediately

After malloc(1GB), no physical RAM is allocated. The OS maps virtual pages but marks them as not-present. Physical frames are assigned only when you actually write to each page (demand paging).

The one-line summary of each
Cache: tiny, blazing-fast SRAM that hides RAM latency — exploit spatial/temporal locality
RAM: the working memory everything runs from — volatile, limited, and the bottleneck
VRAM: bandwidth-optimized GPU memory — parallel reads for textures, tensors, frames
Virtual: the OS illusion that every process has its own huge private address space
