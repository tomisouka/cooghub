B-Tree.

Multi-Key · Multi-Child · Disk-Optimized
search O(log n)
insert O(log n)

height O(log_m n)
1 — Multiple Keys Per Node
A BST node holds one key, has two children. A B-tree node holds many keys, has many children. Keys in a node are sorted. Between every pair of adjacent keys sits a child pointer — everything in that subtree falls between those two keys.
BST Node — 1 key, 2 children
B-Tree Node (order 4) — 3 keys, 4 children
Order m = max children per node. Each node holds at most m−1 keys and at most m children. More keys per node = shorter tree = fewer disk reads.
2 — The Rules of a B-Tree (Order m)
These rules keep the tree balanced and nodes dense enough to be useful. Every rule exists to minimize disk reads.
1Every node has at most m children and at most m−1 keys.
2Every non-root node has at least ⌈m/2⌉ children — nodes must stay at least half full.
3The root has at least 2 children (unless it is a leaf).
4All leaves are at the same depth — the tree is always perfectly height-balanced.
5Keys within a node are sorted. The subtree between key[i] and key[i+1] contains only values between those two keys.
3 — A Full B-Tree of Order 3
Order 3 — each node holds at most 2 keys and at most 3 children. Minimum 1 key per non-root node. All leaves at the same level.
Root [30|60] splits the tree into three ranges: <30, 30–60, >60. Each internal node further splits its range. Every leaf is at depth 2. No node exceeds 2 keys.
4 — Node Split — What Happens When a Node is Full
When a node reaches m keys it's overfull. The middle key gets promoted up to the parent. The remaining keys split into two new nodes.
Insert 45 — node becomes overfull (3 keys in order-3 tree)
→
Split — 45 promoted, [30] and [60] become siblings
Split rule: middle key goes up, left keys stay left, right keys stay right. If the parent is also full it splits too — this can cascade all the way to the root. If the root splits, tree height increases by 1.
5 — BST vs B-Tree

Keys per node 1 1 to m−1
Children per node 0, 1, or 2 ⌈m/2⌉ to m

Height O(n) worst case O(log_m n) — very short
Disk reads to find key O(log n) nodes O(log_m n) — far fewer nodes
Designed for in-memory structures disk storage, databases, file systems
A B-tree of order 1000 on a million records has height ≈ 2. That means at most 2 disk reads to find anything. A BST on the same data could need 20 reads.
Key Properties
Multi-Key Nodes
Each node holds up to m−1 keys and m children. More keys per node = shorter tree = fewer disk reads.
m−1 keys per node
Always Balanced
All leaves are at the same depth — guaranteed. No degenerate case. Height grows only when the root splits.
leaves same depth
Node Split
When a node is full the middle key gets promoted to the parent and the node splits in two. Can cascade up to root.
middle key promotes
Half Full Minimum
Non-root nodes must stay at least ⌈m/2⌉ children — they can't be nearly empty. Keeps nodes dense and the tree short.
⌈m/2⌉ minimum
Used In
Databases (PostgreSQL, MySQL indexes), file systems (NTFS, ext4, HFS+), and anywhere disk I/O is the bottleneck.
