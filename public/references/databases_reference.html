History of Databases
From punch-card file systems to distributed cloud-native stores
1950s
Flat File & Tape Storage
Data stored as sequential records on magnetic tape. No querying — programs read files top to bottom. Updating meant rewriting the entire file. The "database" was just the file system.
1960 — IMS (IBM)
Hierarchical Model
IBM's Information Management System — the first real DBMS, built for NASA's Apollo program. Data stored as parent-child trees. Fast for known access paths, catastrophic for unexpected queries. Still runs some banking systems today.
1969 — CODASYL
Network Model
Proposed by Charles Bachman. Records linked via pointers in a graph (not just trees). More flexible than hierarchical but required developers to navigate relationships manually — like traversing pointers in C.
1970 — Codd's Paper
Relational Model Born
Edgar F. Codd at IBM publishes "A Relational Model of Data for Large Shared Data Banks." Proposes storing data in tables (relations) with rows and columns. Data accessed by what it is, not where it is physically stored. Revolutionizes the field.
1974–1979
SQL & First Relational Systems
IBM's System R prototype implements SEQUEL (later SQL). Oracle releases the first commercial SQL RDBMS in 1979. IBM follows with DB2. The relational era begins in earnest.
1980s–1990s
RDBMS Dominance
Oracle, Sybase, SQL Server, and PostgreSQL mature. ACID transactions become the gold standard. Object-oriented databases emerge but fail to displace relational. The web era arrives and MySQL becomes the go-to for web apps.
2004–2009
NoSQL Movement
Google's Bigtable (2006) and Amazon's Dynamo (2007) papers spark a revolution. Facebook, Twitter, and LinkedIn need to scale beyond what single-node SQL can handle. MongoDB, Cassandra, Redis, and CouchDB emerge. CAP theorem enters the conversation.
2010s
NewSQL & Polyglot Persistence
NewSQL (Google Spanner, CockroachDB, TiDB) attempts to combine SQL's ACID guarantees with NoSQL's horizontal scale. Teams start using multiple database types for different workloads — relational for transactions, Redis for caching, Elasticsearch for search.
2020s
Cloud-Native & Serverless
PlanetScale, Supabase, Neon, Turso, and D1 bring serverless relational databases. Vector databases (Pinecone, pgvector) emerge for AI workloads. The line between cache, database, and message queue continues to blur.
Database Models Hierarchy
Every model is an answer to a different question about how data relates
Hierarchical
Tree Structure
Data organized as parent → child nodes. Each child has exactly one parent. Fast traversal for known paths, inflexible for unexpected relationships.

Think: file system, org chart, XML.
IMSWindows RegistryXML/JSON docs
Network
Graph of Pointers
Like hierarchical but children can have multiple parents. Records linked via explicit physical pointers. Powerful but requires navigational programming — you walk the graph manually.

Think: a road map with intersections.
IDMSCODASYL
Relational
Tables + Foreign Keys
Data in rows/columns. Relationships via foreign keys. You declare what you want (SQL), not how to get it. The query optimizer figures out execution.

Think: a spreadsheet where sheets reference each other.
PostgreSQLMySQLSQLiteOracle
Document
JSON/BSON Collections
Data stored as self-contained documents (JSON/BSON). No fixed schema — each document can have different fields. Great for nested, variable-structure data.

Think: a folder of JSON files you can query.
MongoDBCouchDBFirestoreDynamoDB
Key-Value
Dictionary at Scale
Simplest model — every value has a unique key. Extremely fast lookups O(1). No structure imposed on values. Best for caching, sessions, leaderboards.

Think: a giant JS object / Python dict.
RedisMemcachedDynamoDBetcd
Column-Family
Wide Rows
Stores data by column groups rather than rows. Extremely efficient for write-heavy workloads and time-series data. Columns not present in a row simply don't exist — no NULLs.

Think: a spreadsheet where each row can have completely different columns.
CassandraHBaseBigtable
Graph
Nodes + Edges
Data modeled as entities (nodes) and relationships (edges), both with properties. Queries traverse relationships natively — no expensive JOINs.

Think: social networks, recommendation engines, knowledge graphs.
Neo4jArangoDBAmazon Neptune
Vector
Embeddings Store
Stores high-dimensional vectors (embeddings from ML models). Queries find nearest neighbors by semantic similarity, not exact match. The backbone of modern AI search.

Think: "find things that mean the same thing."
PineconepgvectorWeaviateChroma

StandardYearKey additions
SQL-861986First ANSI standard. Basic SELECT, INSERT, UPDATE, DELETE. WHERE clauses. Joins.
SQL-891989Integrity constraints (PRIMARY KEY, FOREIGN KEY, NOT NULL). Minor fixes.
SQL-921992Huge leap. OUTER JOINs, CASE expressions, subqueries, CAST, string functions, date/time types, transaction isolation levels. Still the baseline most devs learn.

JS → Real Database
How to migrate from hardcoded JS constants (like this app) to a real database — step by step
Step 1 — Recognize the pain points
When do you need a database?
Hardcoded JS is fine when data is static and only you edit it. You need a DB when:
• Content changes frequently (you're editing subjects.js every week)
• Multiple people need to add/edit content
• You want to track state per user (flashcard progress, last-viewed, scores)
• Data grows large enough that rebuilding the app to update it is annoying
Step 2 — Choose your database
For a local study app like Coogs Hub
SQLite (via Drizzle ORM) is the best fit — it's a single file, zero server, and works perfectly for local-first apps. If you ever want to sync across devices, Turso extends SQLite to the cloud with zero config changes.

Alternatives: PocketBase (all-in-one backend, great for solo devs), Supabase (PostgreSQL with auth and realtime, if you want a full backend).
Step 3 — Design your schema
Map your JS data shapes to tables
Every JS constant becomes a table. Every array item becomes a row. Every nested object might become a separate table with a foreign key.
// Your current JS shape:
const course = {
  id: "datastruct",
  label: "Data Structures",
  courseCode: "COSC 2436",
  color: "#e8c547",
  notes: [{ file: "...", label: "..." }],  // → separate table
  flashcards: "dsa_basics",
};

-- Becomes these SQL tables:
CREATE TABLE courses (
  id        TEXT PRIMARY KEY,
  label     TEXT NOT NULL,
  course_code TEXT,
  color     TEXT,
  dept_id   TEXT REFERENCES departments(id)
);

CREATE TABLE course_notes (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  course_id TEXT REFERENCES courses(id),
  label     TEXT,
  file_path TEXT,
  sort_order INTEGER
);
Step 4 — Seed the database
Write a one-time migration script
Import your existing JS constants and insert them into the database. Run once. You'll never touch the JS constants again after this.
// scripts/seed.js
import { db } from "./db.js";
import { ALL_COURSES } from "../src/data/subjects.js";

for (const course of ALL_COURSES) {
  db.run(
    `INSERT INTO courses (id, label, course_code, color) VALUES (?, ?, ?, ?)`,
    [course.id, course.label, course.courseCode, course.color]
  );
  for (const note of course.notes) {
    db.run(
      `INSERT INTO course_notes (course_id, label, file_path) VALUES (?, ?, ?)`,
      [course.id, note.label, note.file]
    );
  }
}
Step 5 — Replace imports with queries
Swap JS constants for DB calls in your components
Your React components currently import from subjects.js. After migration, they call an API route or a local DB client instead.
// Before (hardcoded):
import { getCourse } from "../data/subjects";
const course = getCourse("datastruct");

// After (database — using Drizzle + SQLite):
const course = await db
  .select()
  .from(courses)
  .where(eq(courses.id, "datastruct"))
  .get();

// Or with a simple API route (Express/Hono):
const course = await fetch(`/api/courses/datastruct`)
  .then(r => r.json());
Step 6 — Add a UI to edit content
The payoff — no more editing JS files
Once data lives in a DB, you can build a simple admin UI: add a course, upload a note, edit a label — all without touching code. For a solo study app, even a basic form that INSERTs into SQLite is a massive quality-of-life upgrade.

Recommended stack for Coogs Hub migration:
• better-sqlite3 — synchronous SQLite for Node, fastest option
• Drizzle ORM — TypeScript-first, generates migrations from your schema
• Hono — lightweight API server (or just extend the existing Express server)
• PocketBase — if you want an all-in-one option with a built-in admin panel
