What Pseudocode Is — And Is Not
THE MINDSET BEFORE YOU WRITE A SINGLE LINE
▶
Read this first
foundation not Python, not C++, not math precise English + math notation
The Core Idea
Pseudocode Lives Between English and Code
1
The purpose: communicate the algorithm, not implement it
Pseudocode communicates the idea of the algorithm clearly enough that any competent programmer could implement it in any language. It is not code. You should not be thinking about syntax, data types, or language-specific details.

The reader of your pseudocode is the grader — they want to see that you understand what the algorithm is doing, in what order, and why.
2
The right level of abstraction — use math when it's cleaner
When the math is clearer than code, use math. \(\text{max}(A[j..i])\) is better than a nested loop computing the max. \(\text{Sort}(A)\) is better than writing a sorting algorithm inline. If a subroutine is standard and you've described it elsewhere, just call it by name.
Good abstraction levelp ← KthClosest(R, ⌈m/2⌉) — fine, you already defined KthClosest.
running_max ← max(running_max, A[j]) — fine, max is understood.
S₁ ← {z ∈ S : d(z) < d(p)} — fine, set-builder notation is clear.
3
The reader test — would any CS student understand this?
After writing a line of pseudocode, ask: "could a CS junior implement this in Python or Java without asking me anything?" If yes, the level is right. If they'd need to ask "what does that mean exactly?", it's too vague. If they'd need to know Python-specific syntax, it's too specific.
✕ Too Vague
Find the closest points.
Use the pivot to split.
Combine the results.
Return the answer.
No structure, no specifics, unimplementable.
✓ Right Level
p ← KthClosest(R, ⌈m/2⌉)
S₁ ← {z ∈ S : d(z) < d(p)}
if |S₁| = k−1: return p
else if |S₁| > k−1:
  return KthClosest(S₁, k)
else: return KthClosest(S₂, k−|S₁|−1)
Precise logic, uses math notation, implementable.
✕ Too Specific (Code)
max_val = float('-inf')
for i in range(len(arr)):
  if arr[i] > max_val:
    max_val = arr[i]
return max_val
This is Python. Pseudocode shouldn't be language-specific.
✓ Right Level
max ← −∞
for i ← 1 to n:
  if A[i] > max: max ← A[i]
return max
Language-agnostic, uses ← for assignment, clear loops.

Structure — Every Algorithm Has the Same Skeleton
THE 4 PARTS EVERY PSEUDOCODE BLOCK MUST HAVE
▶
Before writing a single line, identify these four things
input declaration output declaration base case main logic
The 4-Part Skeleton
Anatomy of a Pseudocode Block
1
Start with the header — name your function and declare I/O
The function name should say what it does. Parameters should be named meaningfully. The output (comment or explicit) should say what you return. This is the "contract" that correctness proofs refer to.
Good headersfunc KthClosest(S, k) — Output: k-th closest point to origin.
func CleaningRobot(grid[0..m-1][0..n-1]) — Output: max dirty cells cleaned.
func FindCandidate(A[1..n]) — Output: (candidate, count) or (∅, 0).
2
Write the base case immediately after the header
Before writing any logic, ask: "what's the smallest input where the answer is trivial?" Write that check first. This ensures the recursion terminates and gives graders a clean entry point for the correctness argument.
Base cases by algorithm typeD&C: n=1 (single element). DP iteration: i=0 or i=1 (first cell). MergeSort: n=1 (already sorted). Binary search: lo > hi (not found). Game: trivially winning/losing position.
3
Main logic — divide it into named phases with comments
Long pseudocode should have phase separators in comments. Graders scan pseudocode; comments act as a table of contents. Each phase should do one thing: decompose, recurse, combine.
Good comment structure▷ Phase 1: partition into groups of 7
▷ Phase 2: find median of medians (pivot)
▷ Phase 3: partition S around pivot
▷ Phase 4: recurse on correct side
Common Mistakes
✕
Missing the base case entirely. Pseudocode without a base case has an infinite recursion — the grader knows you haven't thought through termination.
✕
Unnamed function / unclear I/O. "Algorithm 1: do the thing" — unclear. The header must declare: name, parameters, return value.

▶

The Complete Notation Reference
Standard Pseudocode Notation — All the Symbols
1
Comments: explain WHY, not WHAT
Bad comment: ▷ set running_max to max of running_max and A[j] — this just restates the line. Good comment: ▷ extend group leftward, tracking new max — this explains the purpose in the algorithm's context.
The testIf a comment could be auto-generated by reading the code, it's useless. A good comment tells the reader something they couldn't infer from the code alone — why this step, what invariant it maintains, what edge case it handles.
2
Indentation communicates structure — be consistent
Every level of nesting gets one indent. The grader reads indentation to understand block structure. Inconsistent indentation makes pseudocode ambiguous — they can't tell which block a line belongs to.
Indentation levelsfor loop body: +1 indent. if/else body: +1 indent. Nested if inside for: +2 indent. Recursive call at the same level as other statements: same indent as those statements.
3
1-indexed vs 0-indexed — pick one, state it, stick to it
The textbook uses 1-indexed arrays (A[1..n]). Most pseudocode in this course is 1-indexed. If you use 0-indexed (A[0..n−1]), state it at the top. Mixing the two in the same pseudocode is fatal.
Common Mistakes
✕
Using = for both assignment and comparison. Write x ← 5 for assignment. Write if x = 5 for comparison. Mixing these makes pseudocode ambiguous.
✕
No comments at all, or comments that restate the code. Comments are graded. "▷ initialize dp[0] to 0" is unhelpful. "▷ base case: empty prefix has zero sum" tells the grader you understand the algorithm.
04
D&C Pseudocode — The Recursive Template
HOW SPLIT + RECURSE + COMBINE MAPS TO CODE STRUCTURE
▶
Use for…
MergeSort, QuickSort, Binary Search Linear Select (k-th smallest) FindMinMax, Majority D&C any recursive split-and-combine algorithm
The D&C Template Mapped to Pseudocode Lines
D&C Algorithm Structure → Pseudocode Mapping
1
Tail recursion: combine = recurse and return directly
In some D&C algorithms (QuickSelect, Binary Search), after the divide step you recurse on one side and return its result directly — no combining. This is tail recursion. Your pseudocode should make this explicit: return KthClosest(S₁, k) not result ← KthClosest(S₁, k); return result.
2
Non-tail recursion: both halves + combine
In MergeSort, FindMinMax, and majority D&C: you recurse on both halves and then combine. Your pseudocode should: (1) recursively call both, (2) store both results in variables, (3) combine explicitly.
FindMinMax pattern (maxL, minL) ← FindMinMax(L)
(maxR, minR) ← FindMinMax(R)
overall_max ← larger of maxL, maxR
return (overall_max, smaller of minL, minR)
3
Always name what the recursive call returns — store it in a variable
Don't write KthClosest(S₁, k) as a floating statement. Always either: (a) return it directly return KthClosest(S₁, k), or (b) store it result ← KthClosest(S₁, k). A function call with no assignment and no return is meaningless.
FindMinMax(S[1..n]) Output: (maximum, minimum) element of S
1if n = 1: return (S[1], S[1])  single element is both max and min
2if n = 2: compare S[1] and S[2]  1 comparison settles both
3return (larger, smaller)
4L ← S[1..⌊n/2⌋]   R ← S[⌊n/2⌋+1..n]  split into halves
5(maxL, minL) ← FindMinMax(L)  recurse left — IH: correct by induction
6(maxR, minR) ← FindMinMax(R)  recurse right
7overall_max ← larger of maxL, maxR  1 comparison
8overall_min ← smaller of minL, minR  1 comparison
9return (overall_max, overall_min)
Common Mistakes
✕
Recursive call with no assignment or return. Writing MergeSort(A[1..n/2]) as a standalone line does nothing. Either store the result or return it.
✕
Forgetting to handle both n=1 and n=2 base cases when needed. FindMinMax needs both — if n=2, don't recurse (you'd recurse into n=1 and n=1, spending 2 recursive calls + combine = 2 comparisons instead of 1).

DP Pseudocode — Table Filling and Memoization
HOW THE DP RECURRENCE MAPS TO ITERATIVE TABLE FILLING
▶
Use for…
MaxSum, Knapsack, Grid DP LCS, Edit Distance, Partition DP any problem with overlapping subproblems iterative (bottom-up) DP preferred for clarity
DP Pseudocode = 4 Things in Order
The DP Pseudocode Recipe
1
The fill order must ensure predecessors are always ready
The most common DP bug is filling the table in the wrong order. Before writing the loop, ask: "what does dp[i] depend on?" If it depends on dp[i−1], fill left-to-right. If it depends on dp[i−1][j−1], fill top-left to bottom-right. If it depends on dp[j] for j < i, fill i=0, 1, 2, …, n.
Fill order by DP type 1D DP (dp[i] depends on dp[i−1]): for i ← 1 to n
2D grid DP (dp[i][j] from dp[i−1][j], dp[i][j−1]): nested for i, for j
Interval DP (dp[i][j] depends on dp[i][k] and dp[k][j]): for length ← 2 to n, then i
Partition DP (dp[i] from dp[j−1] for any j ≤ i): for i ← 1 to n
2
State the recurrence as a single assignment line
The heart of the DP pseudocode is the recurrence. It should be a single (possibly multi-option) assignment. Make the "max" or "min" explicit — don't hide it in prose.
Good vs bad ✓ dp[i][j] ← grid[i][j] + max(dp[i−1][j], dp[i][j−1])
✗ "we take the best of moving from above or from the left and add the current cell's value"
3
Separate initialization from the main loop
Base cases (dp[0] = 0, dp[0][j] = −j, etc.) must be set before the main loop — not inside it. A common mistake is trying to handle base cases with if-statements inside the loop, which clutters the recurrence and makes the logic hard to follow.
CleaningRobot(grid[0..m-1][0..n-1]) Output: max dirty cells cleaned; path stored in parent table
1initialize base cases
2dp[0][0] ← grid[0][0]
3for j ← 1 to n−1: dp[0][j] ← dp[0][j−1] + grid[0][j]  top row: right only
4for i ← 1 to m−1: dp[i][0] ← dp[i−1][0] + grid[i][0]  left col: down only
5fill table bottom-up, row by row
6for i ← 1 to m−1:
7for j ← 1 to n−1:
8dp[i][j] ← grid[i][j] + max(dp[i−1][j], dp[i][j−1])  pick up dirt, come from best direction
9return dp[m−1][n−1]  answer: max dirty cells on any path to bottom-right
Common Mistakes
✕
Not initializing dp[0] before the loop. If you handle dp[0] inside the loop with an if-statement, your code is harder to read and easier to get wrong. Initialize base cases before the loop, always.
✕
Wrong fill order — accessing unfilled cells. If dp[i] depends on dp[i+1], you must fill right-to-left, not left-to-right. Always trace through your fill order with a small example to verify.

Greedy Pseudocode — Sort, Select, Commit
ONE PASS, ONE DECISION PER STEP, NO BACKTRACKING
▶
Use for…
Kruskal, Prim, Dijkstra Huffman coding Job scheduling, buy order any "make best local choice" algorithm
Greedy Pseudocode = Sort + One-Pass Decision Loop
1
Greedy algorithms usually have the same structure
Step 1: Sort (or build a priority queue) by the greedy key.
Step 2: Iterate through the sorted order.
Step 3: At each step, greedily make the locally optimal choice.
Step 4: Add to the solution if feasible (or always add, depending on the problem).

The critical question: what is the greedy key? Derive it from the exchange argument before writing any pseudocode.
Greedy keys in this course Job scheduling: sort by profit descending.
Buy order: sort by growth rate r_j descending.
Huffman: always pick two lowest-frequency nodes.
Kruskal: sort edges by weight ascending.
Dijkstra: always pick vertex with smallest current distance.
2
The greedy key comes from the exchange argument — derive it first
Don't guess the sort order. Derive it: "if item A comes before item B in the wrong order, can I swap them and improve?" The condition under which swapping improves tells you the greedy key.

For buy order: swap is better iff r_k > r_j → sort by r descending.
For job scheduling: swap is better (value doesn't decrease) when p_a ≥ p_b → sort by profit descending.
BuyOrder(r[1..n]) Output: order to buy n software products minimizing total cost
1greedy key: fastest-growing rate first (proved by exchange argument)
2Sort products in decreasing order of r_j  O(n log n)
3total_cost ← 0
4for t ← 0 to n−1:  buy one per month
5total_cost ← total_cost + 100 · r[t+1]^t  sorted order: r[1] ≥ r[2] ≥ ...
6return total_cost  and the sorted order
GreedyJobSequencing(jobs[1..n]) Output: feasible subset F of jobs maximizing total profit
1Sort jobs in decreasing order of profit p_i  greedy key
2F ← {jobs[1]}  start with highest-profit job
3for k ← 2 to n:
4if IsFeasible(F ∪ {jobs[k]}):  check sorted-deadline condition
5F ← F ∪ {jobs[k]}
6return F
Common Mistakes
✕
Not deriving the greedy key. Writing "sort somehow" without stating the key. The key must be derived and justified — from the exchange argument — before appearing in pseudocode.
✕
Omitting the feasibility check. In job scheduling, not every job in sorted order gets added — only if it keeps the solution feasible. Leaving out the IsFeasible call makes the algorithm incorrect.

The Top 7 Pseudocode Traps
WHAT GRADERS ACTUALLY LOOK FOR — AND WHAT KILLS POINTS
▶
Check your pseudocode against all of these before submitting
common point deductions
The Checklist
Trap 1 — Missing Base Case
✕
No termination condition. Every recursive algorithm and every DP loop must have a base case. Graders check this first. A recursive algorithm with no base case is infinite — it proves you haven't thought through termination.
Trap 2 — Undefined Variables
✕
Using a variable before defining it. Every variable used in the body must be either: (a) a function parameter, (b) initialized before use, or (c) a standard constant like ∞ or ∅. Using running_max in line 6 without initializing it in line 5 is an error.
Trap 3 — Floating Function Calls
✕
Recursive call with no assignment or return. MergeSort(A[1..n/2]) as a standalone line does nothing in a function that returns a value. Either L ← MergeSort(A[1..n/2]) or return MergeSort(...).
Trap 4 — Off-by-One on Loop Bounds
✕
Wrong loop bounds causing index errors. Common: for i ← 1 to n (correct for 1-indexed), for i ← 0 to n (one too many), for j ← i downto max(1, i-k) (should be max(1, i-k+1)). Trace through a small example to verify bounds.
Trap 5 — No Comments on Non-Trivial Steps
✕
Uncommented algorithm phases. If the grader has to work to understand what each section does, you lose points. Every non-obvious step needs a comment. "▷ median of medians guarantees ≥2n/7 elements on each side" is much better than nothing.
Trap 6 — Pseudocode = Python
✕
Language-specific syntax in pseudocode. arr.append(x), len(arr), range(n), float('inf') — these are Python, not pseudocode. Use: add x to S, |S|, 1 to n, ∞. The course explicitly says pseudocode ≠ code.
Trap 7 — Pseudocode Doesn't Match the Described Algorithm
✕
Inconsistency between description and pseudocode. If your written description says "sort by profit descending" and your pseudocode sorts ascending, you lose points. If your description says "last group" pattern and your pseudocode implements something different, that's a disconnect. Pseudocode must faithfully implement the algorithm you described.
The 30-Second Self-Check
RUN THIS BEFORE SUBMITTING
▶

1. Does every recursive call have a base case that terminates it?

2. Is every variable defined before it's used?

3. Does every function call store or return its result?

4. Trace through the algorithm with a 3–4 element example. Does it give the right answer?

5. Does the pseudocode match what you said in the description?

6. Are comments explaining WHY each non-trivial step exists?

7. No Python/Java/C++ syntax anywhere?
