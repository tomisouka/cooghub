Basics & Structure

SQL (Structured Query Language) is used to create, read, update, and delete data in relational databases. Data is organized into tables (rows and columns). SQL is case-insensitive for keywords, but convention is UPPERCASE for keywords and lowercase for identifiers.

SELECT Queries

SELECT is the most-used SQL statement. It retrieves rows from one or more tables. Every clause is optional except SELECT itself.

Query Clause Order

SELECT [DISTINCT] columns -- 5. pick columns FROM table -- 1. source table(s) JOIN other_table ON condition -- 2. combine tables WHERE row_condition -- 3. filter rows GROUP BY grouping_columns -- 4. group rows HAVING group_condition -- 5. filter groups ORDER BY sort_columns [ASC|DESC] -- 6. sort results LIMIT n OFFSET m; -- 7. paginate

SELECT Syntax

-- All columns SELECT * FROM employees; -- Specific columns SELECT first_name, last_name, salary FROM employees; -- Aliases (rename output) SELECT first_name AS name, salary * 12 AS annual_pay FROM employees; -- Distinct (remove duplicates) SELECT DISTINCT department FROM employees; -- Computed columns SELECT name, price, price * 0.9 AS discounted FROM products;

Filtering & Sorting

WHERE Clause

-- Basic conditions WHERE age > 30 WHERE name = 'Alice' WHERE salary BETWEEN 50000 AND 100000 -- inclusive WHERE city IN ('NYC', 'LA', 'Chicago') -- match list WHERE name LIKE 'A%' -- starts with A WHERE name LIKE '%son' -- ends with son WHERE name LIKE '_ob' -- _ matches one char WHERE email IS NULL -- check for NULL WHERE email IS NOT NULL -- Combine conditions WHERE age > 30 AND department = 'Sales' WHERE city = 'NYC' OR city = 'LA' WHERE NOT status = 'inactive'

Joins

Joins combine rows from two or more tables based on a related column. The ON clause specifies how rows match. Always qualify column names with table.column when joining to avoid ambiguity.

Join Types

TypePlain EnglishReturns
INNER JOINonly matching rowsRows that have a match in BOTH tables — most common
LEFT JOINall left + matchesAll rows from left table; NULL for no right match
RIGHT JOINall right + matchesAll rows from right table; NULL for no left match
FULL OUTER JOINeverythingAll rows from both; NULL where no match on either side
CROSS JOINevery comboCartesian product — every row × every row (no ON needed)
SELF JOINjoin table to itselfUse aliases: find employees and their managers in same table

Join Examples

-- INNER JOIN: only employees with a department SELECT e.name, d.name AS dept FROM employees e INNER JOIN departments d ON e.dept_id = d.id; -- LEFT JOIN: all employees, even those without a dept SELECT e.name, d.name AS dept FROM employees e LEFT JOIN departments d ON e.dept_id = d.id; -- Multiple joins SELECT o.id, c.name, p.title FROM orders o JOIN customers c ON o.customer_id = c.id JOIN products p ON o.product_id = p.id; -- Self join: employee + manager name SELECT e.name AS employee, m.name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.id; -- Find unmatched rows (anti-join pattern) SELECT e.name FROM employees e LEFT JOIN departments d ON e.dept_id = d.id WHERE d.id IS NULL; -- employees with no department

Aggregates & Grouping

Aggregate functions collapse multiple rows into a single value. They're used with GROUP BY to compute values per group. Use HAVING to filter groups (not WHERE, which filters rows before grouping).

Aggregate Functions

FunctionPlain EnglishNotes
COUNT(*)how many rows?Counts all rows including NULLs
COUNT(col)how many non-null?Ignores NULLs in the column
COUNT(DISTINCT col)how many unique?Counts unique non-null values
SUM(col)totalIgnores NULLs; use COALESCE to treat NULL as 0
AVG(col)averageIgnores NULLs — may not be what you expect
MIN(col)smallest valueWorks on numbers, dates, and text
MAX(col)largest valueWorks on numbers, dates, and text

GROUP BY & HAVING

-- Count employees per department SELECT department, COUNT(*) AS headcount FROM employees GROUP BY department; -- Average salary per department (only depts with avg > 70k) SELECT department, AVG(salary) AS avg_salary FROM employees GROUP BY department HAVING AVG(salary) > 70000 ORDER BY avg_salary DESC; -- Multiple grouping columns SELECT department, job_title, COUNT(*) AS count FROM employees GROUP BY department, job_title; -- WHERE vs HAVING -- WHERE filters rows BEFORE grouping -- HAVING filters groups AFTER grouping SELECT department, COUNT(*) AS cnt FROM employees WHERE hire_date > '2020-01-01' -- filter rows first GROUP BY department HAVING COUNT(*) > 5; -- then filter groups

Subqueries

A subquery is a query nested inside another query. They can appear in SELECT, FROM, or WHERE clauses. CTEs are often more readable for complex subqueries.

Subquery Patterns

-- WHERE subquery: employees earning above average SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); -- IN subquery: employees in specific departments SELECT name FROM employees WHERE dept_id IN (SELECT id FROM departments WHERE location = 'NYC'); -- EXISTS subquery: customers who placed at least one order SELECT name FROM customers c WHERE EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.id ); -- FROM subquery (derived table / inline view) SELECT dept, avg_sal FROM (SELECT department AS dept, AVG(salary) AS avg_sal FROM employees GROUP BY department) AS dept_avgs WHERE avg_sal > 60000; -- Correlated subquery: references outer query SELECT name, salary, (SELECT AVG(salary) FROM employees e2 WHERE e2.department = e1.department) AS dept_avg FROM employees e1;

Subquery Keywords

KeywordPlain EnglishUse
INvalue is in subquery resultWHERE id IN (SELECT ...)
NOT INvalue not in subquery resultCareful with NULLs — use NOT EXISTS instead
EXISTSsubquery returns any rowsStops at first match; efficient for large datasets
NOT EXISTSsubquery returns no rowsAnti-join; safer than NOT IN with NULLs
ANY / SOMEmatches at least oneWHERE salary > ANY (SELECT ...)
ALLmatches all valuesWHERE salary > ALL (SELECT ...)

DDL — Defining Tables

DDL (Data Definition Language) creates and modifies the structure of your database. DDL statements are usually auto-committed — there's no rollback in most databases.

CREATE TABLE

CREATE TABLE employees ( id INT PRIMARY KEY AUTO_INCREMENT, first_name VARCHAR(50) NOT NULL, last_name VARCHAR(50) NOT NULL, email VARCHAR(100) UNIQUE NOT NULL, salary DECIMAL(10,2) DEFAULT 0.00, hire_date DATE DEFAULT CURRENT_DATE, dept_id INT, FOREIGN KEY (dept_id) REFERENCES departments(id) ); -- Create from existing table CREATE TABLE emp_backup AS SELECT * FROM employees;

ALTER TABLE

-- Add a column ALTER TABLE employees ADD COLUMN phone VARCHAR(20); -- Modify a column type ALTER TABLE employees MODIFY COLUMN salary DECIMAL(12,2); ALTER TABLE employees ALTER COLUMN salary TYPE DECIMAL(12,2); -- PostgreSQL -- Rename a column ALTER TABLE employees RENAME COLUMN phone TO mobile; -- Drop a column ALTER TABLE employees DROP COLUMN mobile; -- Add a constraint ALTER TABLE employees ADD CONSTRAINT chk_salary CHECK (salary >= 0);

DROP & TRUNCATE

CommandPlain EnglishNotes
DROP TABLEdelete table + all dataPermanent — no undo. Use IF EXISTS to avoid errors
TRUNCATE TABLEdelete all rows, keep structureFaster than DELETE; resets auto-increment; not always rollback-able
DROP DATABASEdelete entire databaseDeletes all tables, views, and data — irreversible

DML — Modifying Data

INSERT

-- Insert one row INSERT INTO employees (first_name, last_name, email, salary) VALUES ('Alice', 'Smith', 'alice@example.com', 75000); -- Insert multiple rows INSERT INTO employees (first_name, last_name, email) VALUES ('Bob', 'Jones', 'bob@example.com'), ('Carol', 'White', 'carol@example.com'); -- Insert from SELECT INSERT INTO emp_backup SELECT * FROM employees WHERE hire_date < '2020-01-01';

UPDATE

-- Update specific rows UPDATE employees SET salary = salary * 1.10, updated_at = CURRENT_TIMESTAMP WHERE department = 'Engineering'; -- Update with subquery UPDATE employees SET dept_id = (SELECT id FROM departments WHERE name = 'HR') WHERE job_title = 'HR Manager'; -- WARNING: UPDATE without WHERE updates ALL rows!

DELETE

-- Delete specific rows DELETE FROM employees WHERE hire_date < '2010-01-01'; -- Delete with subquery DELETE FROM orders WHERE customer_id IN (SELECT id FROM customers WHERE status = 'banned'); -- Delete all rows (with rollback ability, unlike TRUNCATE) DELETE FROM temp_table; -- WARNING: DELETE without WHERE deletes ALL rows!

UPSERT (Insert or Update)

-- PostgreSQL: INSERT ... ON CONFLICT INSERT INTO products (id, name, price) VALUES (1, 'Widget', 9.99) ON CONFLICT (id) DO UPDATE SET price = EXCLUDED.price; -- MySQL: INSERT ... ON DUPLICATE KEY UPDATE INSERT INTO products (id, name, price) VALUES (1, 'Widget', 9.99) ON DUPLICATE KEY UPDATE price = VALUES(price);

Constraints

Constraints enforce data integrity rules at the database level — they prevent bad data from being inserted or updated regardless of the application layer.

ConstraintPlain EnglishNotes
PRIMARY KEYunique row identifierUnique + NOT NULL; one per table; can be composite
FOREIGN KEYlink to another tableValue must exist in referenced table; enables JOINs
UNIQUEno duplicate valuesNULL is usually allowed (and doesn't count as duplicate)
NOT NULLvalue requiredColumn must always have a value; never NULL
CHECKcustom value ruleCHECK (age >= 0 AND age <= 150)
DEFAULTfallback valueDEFAULT CURRENT_TIMESTAMP — used if not specified

Foreign Key Actions

FOREIGN KEY (dept_id) REFERENCES departments(id) ON DELETE CASCADE -- delete child rows when parent deleted ON DELETE SET NULL -- set foreign key to NULL ON DELETE RESTRICT -- block deletion if children exist (default) ON UPDATE CASCADE -- update child FK when parent PK changes

Indexes

Indexes speed up SELECT queries by creating a sorted lookup structure. They slow down writes (INSERT/UPDATE/DELETE) because the index must be updated. Index columns used in WHERE, JOIN ON, and ORDER BY clauses.

-- Create an index CREATE INDEX idx_emp_email ON employees(email); -- Unique index (also enforces uniqueness) CREATE UNIQUE INDEX idx_emp_email ON employees(email); -- Composite index — order matters! CREATE INDEX idx_name ON employees(last_name, first_name); -- Drop an index DROP INDEX idx_emp_email; -- most databases DROP INDEX idx_emp_email ON employees; -- MySQL
TypePlain EnglishUse For
B-Tree (default)balanced tree lookupEquality, range, ORDER BY — the standard choice
UNIQUEenforces no duplicatesEmail, username — uniqueness + speed
Compositemulti-column indexQueries that filter on multiple columns; left-prefix rule
Partialindex a subset of rowsWHERE is_active = TRUE — only index relevant rows
Full-Textsearch inside textMATCH ... AGAINST — document/keyword search

Views & CTEs

Views — Saved Queries

A view is a named saved query that behaves like a virtual table. It simplifies complex queries and provides a security layer by exposing only certain columns.

-- Create a view CREATE VIEW active_employees AS SELECT id, first_name, last_name, email, department FROM employees WHERE status = 'active'; -- Query a view like a table SELECT * FROM active_employees WHERE department = 'Sales'; -- Update a view definition CREATE OR REPLACE VIEW active_employees AS SELECT id, first_name, last_name FROM employees WHERE status = 'active'; -- Drop a view DROP VIEW active_employees;

CTEs — Common Table Expressions

CTEs (introduced with WITH) create named temporary result sets for a single query. They dramatically improve readability over nested subqueries and can reference themselves for recursive queries.

-- Basic CTE WITH dept_stats AS ( SELECT department, AVG(salary) AS avg_sal, COUNT(*) AS cnt FROM employees GROUP BY department ) SELECT * FROM dept_stats WHERE avg_sal > 70000; -- Multiple CTEs WITH high_earners AS ( SELECT * FROM employees WHERE salary > 100000 ), their_departments AS ( SELECT DISTINCT dept_id FROM high_earners ) SELECT d.name FROM departments d JOIN their_departments td ON d.id = td.dept_id; -- Recursive CTE: traverse org chart WITH RECURSIVE org_chart AS ( -- Base case: top-level manager (no manager) SELECT id, name, manager_id, 0 AS level FROM employees WHERE manager_id IS NULL UNION ALL -- Recursive case: employees reporting to above SELECT e.id, e.name, e.manager_id, oc.level + 1 FROM employees e JOIN org_chart oc ON e.manager_id = oc.id ) SELECT * FROM org_chart ORDER BY level;

Window Functions

Window functions compute values across a set of rows related to the current row — without collapsing them like GROUP BY. They use an OVER() clause to define the window. Available in PostgreSQL, SQL Server, MySQL 8+, SQLite 3.25+.

Window Function Syntax

function_name() OVER ( PARTITION BY column -- divide into groups ORDER BY column -- order within each group ROWS BETWEEN ... -- optional frame clause )

Ranking Functions

SELECT name, department, salary, ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS row_num, RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rank, DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rank, NTILE(4) OVER (ORDER BY salary DESC) AS quartile FROM employees;
FunctionPlain EnglishNotes
ROW_NUMBER()sequential number1, 2, 3, 4 — always unique, no ties
RANK()rank with gaps on tie1, 2, 2, 4 — ties get same rank, next skipped
DENSE_RANK()rank without gaps1, 2, 2, 3 — ties get same rank, no skip
NTILE(n)divide into n bucketsQuartiles, deciles, percentiles
PERCENT_RANK()relative rank 0–1(rank - 1) / (total rows - 1)

Offset & Aggregate Window Functions

SELECT name, salary, hire_date, LAG(salary) OVER (ORDER BY hire_date) AS prev_salary, LEAD(salary) OVER (ORDER BY hire_date) AS next_salary, FIRST_VALUE(salary) OVER (PARTITION BY dept ORDER BY salary DESC) AS dept_max, SUM(salary) OVER (PARTITION BY dept) AS dept_total, AVG(salary) OVER (PARTITION BY dept) AS dept_avg, SUM(salary) OVER (ORDER BY hire_date ROWS UNBOUNDED PRECEDING) AS running_total FROM employees;
FunctionPlain EnglishUse
LAG(col, n)value from n rows backCompare current row to previous (default n=1)
LEAD(col, n)value from n rows aheadCompare current row to next
FIRST_VALUE(col)first value in windowBest/worst in group without subquery

Transactions

A transaction is a group of statements treated as one unit. Either all succeed (COMMIT) or all are undone (ROLLBACK). Transactions follow the ACID properties: Atomicity, Consistency, Isolation, Durability.

Transaction Control

BEGIN; -- start transaction (or BEGIN TRANSACTION) UPDATE accounts SET balance = balance - 100 WHERE id = 1; UPDATE accounts SET balance = balance + 100 WHERE id = 2; COMMIT; -- save all changes permanently -- If something goes wrong: BEGIN; DELETE FROM orders WHERE customer_id = 999; ROLLBACK; -- undo everything since BEGIN -- Savepoints: partial rollback BEGIN; INSERT INTO orders VALUES (...); SAVEPOINT order_saved; INSERT INTO order_items VALUES (...); ROLLBACK TO order_saved; -- undo item insert, keep order COMMIT;

Isolation Levels

LevelPlain EnglishPrevents
READ UNCOMMITTEDsee others' draftsNothing — dirty reads possible
READ COMMITTEDonly see committed dataDirty reads (most DB default)
REPEATABLE READconsistent reads in transactionDirty + non-repeatable reads
SERIALIZABLEfully isolatedAll anomalies — but slowest

PropertyPlain EnglishMeaning

Consistencyvalid state guaranteedData always moves from one valid state to another
Isolationtransactions don't interfereConcurrent transactions behave as if they ran serially
Durabilitycommitted = permanentCommitted changes survive crashes and restarts

Pro Tips

  • SELECT *Avoid SELECT * in production. It returns all columns including ones you don't need, increases network overhead, and breaks if table structure changes. Always name your columns explicitly.
  • NULL comparisonsNever use = NULL or != NULL — they always return FALSE. Always use IS NULL and IS NOT NULL. NULL is not a value, it's the absence of one.
  • WHERE vs HAVINGWHERE filters rows before grouping; HAVING filters groups after aggregation. Using HAVING when WHERE would work is a common performance mistake.
  • NOT IN + NULLsIf any value in a NOT IN list is NULL, the entire expression returns NULL (no rows match). Use NOT EXISTS with a correlated subquery instead — it's safer and often faster.
  • Index column orderComposite indexes follow a left-prefix rule: an index on (a, b, c) helps queries filtering on a or a, b but NOT on b alone. Put the most selective column first.
  • CTEs vs subqueriesCTEs (WITH clause) aren't always faster — they're mainly a readability tool. In PostgreSQL, CTEs are optimization fences (pre-13). Prefer CTEs for clarity; profile both for performance-critical queries.
  • TRUNCATE vs DELETETRUNCATE is much faster for clearing a table because it doesn't log individual row deletions. But it can't be filtered (no WHERE), may not be rollback-able, and resets sequences/auto-increment.
  • EXPLAIN / EXPLAIN ANALYZEAdd EXPLAIN before any query to see the execution plan — whether it's doing full table scans or using indexes. Use EXPLAIN ANALYZE (PostgreSQL) to see actual runtime stats.
  • PaginationLarge OFFSET values are slow — the DB must scan and discard skipped rows. For deep pagination, use keyset/cursor pagination: WHERE id > last_seen_id ORDER BY id LIMIT 20.
  • TransactionsAlways wrap multi-step operations (transfer funds, place orders) in a transaction. Without it, a crash halfway through leaves your data in an inconsistent state.
