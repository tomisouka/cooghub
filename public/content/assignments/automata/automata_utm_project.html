What is the encoding?
The UTM \(U\) operates on a single long string over the alphabet \(\{c, I\}\). This string encodes both a TM \(M\) and an input word \(w\) as \(\langle M, w \rangle\). Understanding the encoding is prerequisite to everything else.

\[ \underbrace{\delta_1 \;cc\; \delta_2 \;cc\; \cdots \;cc\; \delta_k}_{\text{transition encodings}} \;\underbrace{ccc}_{\text{separator}} \;\underbrace{X_{i_1} \;c\; X_{i_2} \;c\; \cdots \;c\; X_{i_n}}_{\text{encoded input word }w} \]
Each \(\delta_j\) encodes one rule \(\delta(q_i, X_j) = (q_k, X_l, d)\) as five I-blocks separated by c's. Rules are separated by cc. The entire TM description is terminated by ccc before the word begins.
Why can't we use both write + move in one step? ▶
Project constraint: Every TM in this project is restricted to either write a symbol or move the head — not both in a single transition. This is a simplification of the standard TM model to make simulation easier. In our Python UTM, we implement each transition as two micro-operations: (1) write the new symbol at the current head position, then (2) move the head in direction \(d\). The head never moves and writes simultaneously.
\[\delta(q_i, X_j) = (q_k, X_l, d) \;\Longrightarrow\; \text{write } X_l \text{ at current cell, then move } d\]
1
Worked example: encode \(\delta(q_1, a) = (q_2, X, R)\)
State \(q_1 \to I\). Symbol \(a = X_2 \to II\). New state \(q_2 \to II\). New symbol \(X = X_4 \to IIII\). Direction \(R \to II\).
\[I \;c\; II \;c\; II \;c\; IIII \;c\; II\]
2
Tape layout for U
Tape 1 (read-only): entire \(\langle M, w \rangle\) string. U scans it to find the applicable transition.
Tape 2 (working): simulated tape of \(M\), initialized with encoded \(w\).
Tape 3 (state): current state of \(M\), initially \(q_1 = I\).
3
How U executes one step
U reads the current state from Tape 3 and the current symbol from Tape 2's head. It then scans Tape 1 left-to-right for a transition block whose first two I-groups match. When found, it updates Tape 2 (write), moves Tape 2's head (direction), and writes the new state to Tape 3.
Start/halt convention: All TMs (including U) start with the tape as #w# and begin at the first blank to the right of the input. After computation, the head halts at the first blank to the right of the output. If there is no output, the machine may halt anywhere. Our simulator implements this: blank = X1 = symbol index 1.
Concept
[SIPSER 3.1] UNIVERSAL TMCHURCH-TURING THESIS
▶

Universal Turing Machine (Sipser Def 3.9): A UTM \(U\) is a TM that can simulate any other TM \(M\) on any input \(w\), given \(\langle M, w \rangle\) as input. This is the theoretical foundation of modern general-purpose computing — every computer is essentially a UTM.

Why the encoding works: Since TMs can only read finite alphabets, we need to encode arbitrary TMs into a fixed alphabet. The \(\{c, I\}\) encoding is a standard construction where \(c\) acts as a structural separator and \(I\) as a unary counter, making it possible to encode any finite state machine.

Exam tip: The key insight is that \(U\) accepts \(\langle M, w \rangle\) iff \(M\) accepts \(w\). This directly implies undecidability of the halting problem — you can't decide in general whether \(U\) halts.

Concept
[SIPSER 3.1] TM DESIGNZIG-ZAG TECHNIQUE
▶

Zig-zag matching: The standard technique for recognizing \(\{a^n b^n\}\) with a TM. It exploits the random-access nature of the tape — unlike a PDA (which uses a stack), the TM can cross off symbols and return to check the current state of crossing off. Each iteration crosses off exactly one \(a\)/\(b\) pair.

Why a PDA can't decide this (but a TM can): A PDA would recognize \(\{a^n b^n\}\) nondeterministically, but TMs are more powerful because they can move left and right and inspect the tape repeatedly.

Exam tip: When \(q_1\) reads blank (B) with no more uncrossed \(a\)'s, all \(a\)'s had matching \(b\)'s (since Y's are skipped, only matched b's are Y). If any uncrossed \(b\) remained, the scan in \(q_2\) would have found it. So reaching \(q_5\) via \(q_1\) reading B is correct acceptance.

Concept
[SIPSER 3.1] TM FUNCTIONSCOMPUTABLE FUNCTIONS
▶

TMs as function computers: A TM doesn't just accept or reject — it can compute a function \(f: \Sigma^* \to \Sigma^*\). When computing \(f(w)\), the TM starts with \(w\) on the tape and halts with \(f(w)\) on the tape. A function is Turing-computable iff some TM computes it.

String copy is fundamental: The ability to duplicate data on the tape is used as a subroutine in many theoretical constructions. It demonstrates that TMs can perform non-trivial data transformation, not just membership testing.

Exam tip: When a TM computes a function, we say it transduces the input. The output is whatever is left on the tape when the TM halts. If it loops, the function is undefined for that input.

Concept
[SIPSER 3.1] UNARY ARITHMETICPRIMITIVE RECURSION
▶

Unary representation: Natural number \(n\) is represented as \(a^n\). Incrementing \(n\) simply appends one more symbol. This is the TM analogue of the successor function \(S(n) = n+1\), which is the most primitive arithmetic operation.

Why this is powerful: Every computable function on natural numbers can be built from the successor function plus composition and primitive recursion (by the Church-Turing thesis). So this tiny TM is the theoretical seed of all computation.

What to submit
The Python simulator implements a three-tape UTM \(U\). Tape 1 holds the encoded \(\langle M, w \rangle\) (parsed into a transition dict for efficiency). Tape 2 is the simulated tape of \(M\). Tape 3 tracks the current state. The code below is the complete submission for Part 1.
Architecture Overview
1
Module structure
Encoding helpers: encode_int, encode_state, encode_symbol, encode_direction, encode_transition, build_utm_input.
Parser: parse_utm_input — splits on ccc, parses each transition block into a dict keyed by (qi, xj).
Tape class: infinite tape backed by a dict[int, int], supporting read, write, move.
UTM class: holds all three tapes, runs the simulation step by step.
2
One step of the simulation
\[\text{read } (q_{\text{cur}}, X_{\text{cur}}) \;\xrightarrow{\text{lookup Tape 1}}\; (q_k, X_l, d)\] \[\text{Tape 2: write } X_l \text{ at head, then move head in direction } d\] \[\text{Tape 3: } q_{\text{cur}} \leftarrow q_k\]
If no transition exists for \((q_{\text{cur}}, X_{\text{cur}})\), the TM halts. This implements both accept (intended halt) and reject (no applicable transition).

"""
utm.py — Three-Tape Universal Turing Machine Simulator
COSC 3340 Spring 2026 · Project Part 1

Encoding alphabet: {c, I}
  - States:   qi = i I's
  - Symbols:  Xj = j I's   (X1=Blank, X2=a, X3=b, X4=X-mark, X5=Y-mark)
  - Direction: L=I, R=II
  - Transition δ(qi,Xj)=(qk,Xl,d): Ii c Ij c Ik c Il c Id
  - Transitions separated by cc, TM ends with ccc, then input word
"""

# ── Encoding helpers ──────────────────────────────────────

def encode_int(n):
    return "I" * n

def encode_transition(qi, xj, qk, xl, d):
    dir_enc = "I" if d == "L" else "II"
    return (encode_int(qi) + "c" + encode_int(xj) + "c" +
            encode_int(qk) + "c" + encode_int(xl) + "c" + dir_enc)

def build_utm_input(transitions, input_symbols):
    tm_enc = "cc".join(encode_transition(*t) for t in transitions)
    word_enc = "c".join("I" * s for s in input_symbols)
    return tm_enc + "ccc" + word_enc

# ── Parser ─────────────────────────────────────────────────

def parse_utm_input(utm_input):
    parts = utm_input.split("ccc")
    tm_part, word_part = parts[0], parts[1]
    transitions = {}
    for raw in tm_part.split("cc"):
        f = raw.split("c")
        qi, xj, qk, xl = len(f[0]), len(f[1]), len(f[2]), len(f[3])
        d = "L" if f[4] == "I" else "R"
        transitions[(qi, xj)] = (qk, xl, d)
    tape = [len(s) for s in word_part.split("c")]
    return transitions, tape

# ── Tape class ─────────────────────────────────────────────

class Tape:
    BLANK = 1
    def __init__(self, initial=None):
        self.cells = {}
        self.head = 0
        if initial:
            for i, s in enumerate(initial): self.cells[i] = s
    def read(self): return self.cells.get(self.head, self.BLANK)
    def write(self, s): self.cells[self.head] = s
    def move(self, d): self.head += 1 if d == "R" else -1

# ── UTM class ──────────────────────────────────────────────

class UTM:
    def __init__(self, utm_input):
        self.transitions, tape_init = parse_utm_input(utm_input)
        self.tape2 = Tape(tape_init)   # simulated tape
        self.state = 1                  # tape3: start at q1
        self.steps = 0

    def step(self):
        sym = self.tape2.read()
        key = (self.state, sym)
        if key not in self.transitions: return False  # halt
        qk, xl, d = self.transitions[key]
        self.tape2.write(xl)           # write (not both!)
        self.tape2.move(d)             # then move
        self.state = qk
        self.steps += 1
        return True

    def run(self):
        while self.steps < 100_000 and self.step(): pass
        return self.get_output()

    def get_output(self):
        if not self.tape2.cells: return [1]
        lo, hi = min(self.tape2.cells), max(self.tape2.cells)
        out = [self.tape2.cells.get(i, 1) for i in range(lo, hi+1)]
        while out and out[0] == 1: out.pop(0)
        while out and out[-1] == 1: out.pop()
        return out if out else [1]
Write-OR-move compliance: In the step() method, tape2.write(xl) and tape2.move(d) are separate calls. The head position does not change during the write. This implements the project constraint that each transition is either a write or a move — we split \(\delta\) into two sequential micro-operations.

Concept
[SIPSER 3.3] HALTING PROBLEMUNDECIDABILITY
▶

Why the UTM implies undecidability: The UTM \(U\) exists and is computable. But the halting problem — deciding whether \(U\) halts on input \(\langle M, w \rangle\) — is undecidable (Sipser Theorem 4.11). The key insight: if a decider for the halting problem existed, we could use diagonalization to construct a TM that contradicts itself.

Halting vs. acceptance: \(U\) accepts \(\langle M, w \rangle\) iff \(M\) accepts \(w\). \(U\) loops iff \(M\) loops on \(w\). \(U\) rejects iff \(M\) rejects \(w\). The language \(A_{TM} = \{\langle M, w \rangle \mid M \text{ accepts } w\}\) is recognizable but not decidable.

Our simulator's limitation: The MAX_STEPS = 100,000 safety limit means our simulator cannot detect infinite loops — it just stops after the limit. A true UTM would run forever when simulating a non-halting TM. This is not a bug; it's the fundamental limitation of computation.

Part (a): What is a Quantum Turing Machine?
▶
A Quantum Turing Machine (QTM), introduced by David Deutsch in 1985, is a theoretical model of computation that extends the classical Turing machine by replacing deterministic or probabilistic transitions with quantum mechanical ones. Formally, a QTM is a tuple \((Q, \Sigma, \delta)\) where the transition function \(\delta: Q \times \Sigma \to \mathbb{C}^{Q \times \Sigma \times \{L, R\}}\) maps each (state, symbol) pair to a probability amplitude distribution over (new state, new symbol, direction) triples. The key difference: a classical TM is in exactly one configuration at each step, while a QTM is in a quantum superposition of multiple configurations simultaneously. A QTM's tape head can be "in multiple positions at once" until a measurement collapses the superposition. The amplitudes must satisfy a unitarity constraint — the evolution of the quantum state must be a unitary (norm-preserving, reversible) linear transformation. This ensures quantum mechanics is respected. Bernstein and Vazirani (1997) gave the first rigorous polynomial-time QTM formalism, enabling formal complexity class definitions.
Part (b): Why is it interesting?
▶
QTMs are interesting for three compounding reasons. First, they challenge the Extended Church-Turing Thesis — the informal claim that any "reasonable" model of computation can be simulated by a probabilistic TM with at most polynomial overhead. Shor's quantum factoring algorithm (1994) runs in polynomial time on a QTM but is believed to require superpolynomial time on any classical TM, suggesting the Extended Church-Turing Thesis may be false. This would represent the most profound complexity-theoretic breakthrough since Cook-Levin. Second, QTMs define the complexity class BQP (Bounded-error Quantum Polynomial time), which contains problems like integer factorization and discrete logarithm — problems on which classical cryptography relies. Third, QTMs are not just theoretical: physical implementations via superconducting qubits, ion traps, and photonic systems are actively being built by Google, IBM, and others. The boundary between theoretical computer science and physical reality is unusually thin here.
Part (c): How does it relate to COSC 3340?
▶
The Quantum TM relates to COSC 3340 at multiple levels. At the model level, a QTM uses the same \((Q, \Sigma, \Gamma, \delta, q_0, q_{accept}, q_{reject})\) skeleton as a classical TM — the difference is in the type of \(\delta\). Any classical TM is a degenerate QTM with all amplitudes in \(\{0, 1\}\). At the computability level, QTMs recognize exactly the same languages as classical TMs: \(L\) is QTM-decidable iff it is classically decidable. Quantum computation does not transcend the Church-Turing Thesis — it cannot decide the halting problem. The undecidability results from class (Sipser Chapter 4–5) still hold. The exciting separation is in complexity, not computability: QTMs can solve some problems faster, not solve fundamentally more problems. This maps directly onto our study of reducibility and complexity hierarchies. Additionally, the \(\langle M, w \rangle\) encoding we implemented in Part 1 is directly used to define \(A_{QTM} = \{\langle M, w \rangle \mid M \text{ is a QTM that accepts } w\}\), which is also undecidable for the same diagonalization reasons.

Concept
BQP vs P vs NPEXTENDED CHURCH-TURING
▶

Complexity landscape with quantum: We know \(P \subseteq BQP\) and \(BQP \subseteq PSPACE\), but whether \(P = BQP\) or \(NP \subseteq BQP\) are open. Shor's algorithm puts FACTORING and DLOG in BQP. Grover's search gives a quadratic speedup for unstructured search, placing some NP problems closer to BQP but not proving \(NP \subseteq BQP\).

Exam connection: The computability boundary (halting problem, Rice's theorem, reductions) is unchanged by quantum. The complexity boundary (P vs NP vs BQP) is the active research frontier. Know which is which.
